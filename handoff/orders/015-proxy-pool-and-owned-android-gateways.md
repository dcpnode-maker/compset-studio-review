# Order 015: proxy health inventory and user-owned Android gateways

The user requests researched, tested proxy candidates and a reusable Android APK so their own phones can provide network routes. This continues Orders012-014; it does not authorize bypass of tool-execution controls, disabling TLS validation, exposing an open relay or transmitting account credentials to public proxy operators.

Scope: existing routes package and tests, new route-health tools and diagnostics, new android-gateway source/build files, docs/proxy-pool-and-android.md and ignored data/routes health artifacts. Root coordinates actual source research and Android build feasibility. A delegated route lane may gather public proxy endpoint lists as untrusted data and perform bounded, unauthenticated HTTPS connectivity/IP-echo probes with valid TLS, short timeouts, finite concurrency and no accommodation-site requests. Distinguish candidate, reachable, independently tested egress, failure and expired states. Reachability is not trust or permission to route authenticated traffic. Preserve separate user-approved routes and explicit source stop/cooldown behavior; no automatic route switching after a challenge, 403 or 429.

Phone gateways must be user-controlled, visible foreground operation with Stop, pairing/authentication, request and traffic limits, no rooting, no CA installation/TLS interception, no sensitive permissions, and no public unauthenticated listener. Prefer same-LAN listener with explicit cellular egress if the phone supports simultaneous networks; devices on shared Wi-Fi do not necessarily provide distinct public IPs. If remote use requires an outbound tunnel, keep it authenticated and do not expose a public listener without a separate reviewed deployment. No claimed universal Android compatibility: state minimum Android/API level, architecture packaging and device proof honestly.

Do not install or execute third-party APKs or scripts from unknown repositories. Inspect primary documentation/source as research; write our own scoped implementation or request any required confirmation before using an unrecognized executable. Official Android/JDK build tools may be used under existing software authorization, but no purchase. Build and static/unit verification do not equal device-tested cellular egress.

Acceptance: actual tested proxy list with measurement destination/time/limits and failure denominator; no trust inflation; Android source and APK if local build is feasible; independently reviewed auth, destination and resource bounds; explicit remaining device pairing/test prerequisites. No phone IP, credential or token committed to Git.

Physical follow-up, 28 September: the reconnected OnePlus10R accepted APK installation and public-certificate fingerprint pairing. The live TLS handshake exposed AndroidKeyStore INCOMPATIBLE_PADDING_MODE in Conscrypt's private RSA operation. Scope includes correcting the key authorization profile against primary Android documentation, selecting that exact identity in the server key manager, preserving old identity material and explicit re-pairing, bumping the internal patch version, independent build/source review and actual verified TLS/neutral egress/Stop evidence. Never solve the compatibility error by disabling authentication, certificate verification, or exporting the private key. Separate frontend work under Order016 continues independently. Proof and limitations belong in docs/android-gateway.md and handoff/reviews/029-android-device-tls.md.

The verified physical diagnostic then found eight public IPv4 answers and eight rejected DNS64 answers matching the selected network's advertised NAT64 prefix. Scope includes a pure, tested DNS-answer helper that may remove only a /96 translated duplicate whose embedded address equals an observed public IPv4 answer from the same response. Preserve original response size bounds, reject every private/null/unsupported/unmatched answer, retain native-answer ordering, and keep a single selected-network lookup and connection with no fallback. Unsupported prefixes and IPv6-only responses remain explicit unsupported cases. No general NAT64/private-address exception or filtering away arbitrary rejected answers is authorized. Independent adversarial tests, review and physical evidence are required before calling the route usable.
