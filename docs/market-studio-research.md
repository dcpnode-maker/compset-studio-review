## Map selection UX recommendation

Build one map-and-table selection workspace. The map answers “where?”; the adjacent filterable table answers “which properties, and why?” Keep one selection model that both views reflect, rather than treating a drawn shape as an implicit competitor list. Show a count with a clear denominator (“located observed candidates in current source/filter”), selected/provisional/unknown decision counts, and unlocated omissions. Each row should expose source, observation time, identity status, relevant size/type attributes, and inclusion/exclusion reasons. Clicking a row focuses its marker and opening its detail loads evidence for that one candidate.

Keep edits transactional: `Draw area` enters a labeled mode; map gestures create a visible draft; `Apply` commits the local filter; `Undo` reverses the last vertex/shape edit; `Cancel` restores the prior committed area; `Clear` returns to all located candidates. Never fetch data because someone pans, draws, resizes, selects a marker, or changes a draft. Make keyboard controls and numeric inputs available beside geometry controls. Save named local sets only through an explicit “Save set” action, retain their source revision/filter snapshot/geometry/date, and label them as local snapshots. A refreshed source revision should prompt the user to re-evaluate stale membership rather than silently rewriting the saved set.

| Shape | Best interaction | Strength | Limitation / recommendation |
| --- | --- | --- | --- |
| Circle | Existing center/radius drag handles, plus numeric radius | Fast “near this hotel” selection; easy to understand and quantify | Keep as default and preserve center/radius editing. |
| Polygon | Click/tap vertices, move pointer to preview edge, drag vertices to refine | Matches PriceLabs’ public map compset flow and real neighborhood boundaries | Best next shape for user-defined areas. Retain vertex undo, validation, apply/cancel, and visible inclusion count. |
| Rectangle | Drag corner-to-corner; editable corners after creation | Quick broad bounding-box selection | Add after polygon only if acceptance/use shows demand; it can include irrelevant areas around coastlines/barriers. |
| Freehand | Press-drag trace, then simplify and edit resulting vertices | Natural for tracing irregular neighborhoods | More error-prone on touch and noisy at high zoom; defer. If added, simplify geometry and always provide vertex edit/undo/cancel. |

## Drawing-library choice for this Leaflet app

**Selected implementation: retain Leaflet and extend the existing tested draft/apply controller with polygon geometry.** This reuses the application's pointer cancellation, request isolation and map-instance lifecycle without adding a dependency. Leaflet-Geoman Free is the best-fit library alternative if future shape/edit requirements outgrow that controller; it is not installed by this order. It documents circle, polygon, rectangle, vertex editing, dragging and common editing modes. The free package is MIT; Geoman marks some advanced tools as Pro/commercial, so do not assume advanced undo/redo is included. [Leaflet-Geoman docs](https://geoman.io/docs/leaflet) · [Geoman free/pro comparison](https://geoman.io/comparisons/leaflet-geoman-vs-leaflet-draw)

| Option | Current stack fit | Edit UX | Cost / migration impact |
| --- | --- | --- | --- |
| Leaflet-Geoman Free | Drop-in plugin for existing Leaflet map | Circle/rectangle/polygon drawing, vertex edits, shape drag and snapping; can be exposed through custom buttons rather than its full toolbar | MIT free package; Pro is commercial. Lowest map-stack disruption. |
| Leaflet.draw | Drop-in Leaflet plugin | Polygon/rectangle/circle drawing and editable feature group; simpler legacy toolbar and edit/delete flow | MIT; no map migration. Better than bespoke code for basic drawing, but less built-in edit tooling than Geoman. [Official docs](https://leaflet.github.io/Leaflet.draw/docs/leaflet-draw-latest.html) |
| MapLibre-Geoman Free | Requires replacing Leaflet renderer and redoing current map integration | Geoman geometry editing, GeoJSON import/export; free package supports core tools | MIT plugin, but map conversion adds implementation, behavior and acceptance cost without a current data scale/performance case. [Docs](https://geoman.io/docs/maplibre) |
| Mapbox GL Draw | Requires Mapbox GL renderer and adapter work | Polygon/line/point drawing and vertex edit through a GL control | OSS drawing package, but introduces Mapbox GL/platform account/usage terms and map-stack migration; poor fit for this local-first app. [Project](https://github.com/mapbox/mapbox-gl-draw) |

None of these should own persistence or determine membership. Keep GeoJSON-like geometry in app state, define boundary semantics (point on boundary counts in), validate finite coordinates/vertex count/area, and compute selection consistently for both map markers and rows. Circle is a distinct radius geometry; rectangle/polygon should use validated geographic geometry. A library’s live edit callbacks should update preview only until Apply.

## Priority

Root also inspected the map image linked by the official PriceLabs custom-compset guide: compact draw/delete/zoom controls, dense observed listing dots and a price-band legend. The selected Studio design keeps the spatial precision but uses labelled drawing actions and an adjacent property list. Price bands are deliberately not inferred for candidates without comparable dated rate evidence. The original Yellow source was inspected for typography, navigation, ribbon grouping and evidence-table density; no proprietary vendor UI code or Yellow domain code was imported.

1. Complete and verify the current Order022 polygon draft against baseline circle behavior; update the contract only after accepted implementation. Keep polygon point/vertex editing accessible and confirm drawing does not trigger collection or stale-response mixing.
2. Add rectangle only if it materially speeds a demonstrated selection task. Defer freehand pending a user workflow and a tested simplification strategy.
3. Deliver synced list/map counts and filters, source/identity badges, stale-source notices, named local saved sets, and inspectable per-candidate evidence before adding estimated metrics.
4. Pursue new market performance metrics only with a documented, sufficiently complete dated dataset and clear calculation basis. Do not imitate Market Dashboard occupancy/ADR/RevPAR/pickup or Revenue Estimator Pro outputs from partial price observations.
5. Treat pricing recommendations, OTA rate updates, live-channel parity, booking history, listing optimizer grades and AI recommendations as separate data/integration products—not visual features a map editor can create.
